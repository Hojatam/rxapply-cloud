1 · Overview

What is this thing?

The test phase is a locally-running, full-fidelity replica of the RxApply production stack, used to validate the 22-agent + 8-workflow architecture before committing to the real build. It runs on your laptop, costs $0, and uses Claude / the Anthropic API as the LLM substrate (with optional multi-provider image gen for Afshin).

The original 12 test scenarios all passed (T1–T12). Phases A→E expanded the stack to its full 21-agent shape, added an operational admin dashboard, fleshed out the proxy with five new HTTP routes, and packaged the n8n trigger surface as five importable workflow JSONs. V2 / Phase F then consolidated everything into a single dashboard, added the 22nd agent (Afshin · designs), shipped a 9-feature control plane (F2–F9 + F6 + F8b), and applied the Report v.1 hardening pass on top.

What the stack actually is, in one sentence each
  • • Anthropic API + Claude / Cowork — runs the agent prompts when LLM inference is needed (Sonnet 4.5 by default); chat is streamed via SSE; cost telemetry tracks tokens × per-token pricing per call.
  • • Postgres (Supabase local) — single source of truth: 23 tables now (16 baseline + agent_journal + the V2 set: prompt_versions, agent_chats, dashboard_settings, media_library, pipelines, agent_actions, plus an image_model_defaults jsonb column).
  • • n8n (Docker) — installed, credentialed, running, with 5 trigger workflows (4 cron + 1 webhook). The proxy now also exposes a full n8n control surface (list/get/run/import/activate via the n8n REST API) so you can drive it from the dashboard without leaving the app.
  • • MailHog (Docker) — a local SMTP sink. Captures every email Ravi, Mehmandar, or any other agent sends so you can inspect them without real delivery.
  • • cowork-proxy (Node, port 7777) — load-bearing control plane. 50+ routes across the F2–F9 + V2.5 features (logs, services, n8n, chat, pipelines, auth/settings/prompts versioning, designs, multi-model defaults, cost, Compose orchestration, per-agent LLM resolver, brand profile injector). Cowork-style helper-running is still there alongside the new feature routes. Now also serves /dashboard directly so the dashboard can be loaded over HTTP instead of file:// (Drawflow CDN works either way).
  • • The 23 agent skills — one folder per agent at agents/<name>/, each with a SKILL.md (instructions for Claude) plus a small Python helper (DB boundary). Afshin (#22) is design-only and uses Claude SVG drafts + paid raster renders. compose-ig (#23, V2.5) is a one-shot agent that generates 3 IG captions + a design plan in a single Anthropic call.
  • • One dashboard — dashboard.html consolidates the V1 test-phase scorecard and the V1 admin operations into a single Tailwind+Drawflow control plane: Overview, Workflows, Agents (with per-agent Run/Chat/History/Forward tabs), Pipelines (visual editor), Compose (per-step pipeline with 3-language output viewer), Logs (L2), Approvals, Designs, Services, Settings (auth + cap + sandbox + image model defaults + per-agent LLM model + Brand profile editor + prompt editor with rollback).
The architectural decision that shaped Phase C. n8n stays a trigger surface, not a logic surface. Every helper is callable directly from the proxy with one HTTP POST, and every cron/webhook in n8n is just "on schedule, POST to /run-helper". This keeps the agent logic in one place (Python helpers + SKILL.md) and avoids the "logic spread across 100 n8n nodes" problem.
Two foundation agents anchor the data layer. Zirak is the only sanctioned writer for agent_journal — every other agent shells out to it after each run with a one-line input/output summary. Paya is the only sanctioned writer for intel_snapshots — it validates payload shape per kind, so the 5 intel agents (Roya, Shahed, Dadbeh, Nasim, Ramin) can drift without breaking Pooya's reader. The schema contract for each kind lives in one file: paya.py.
2 · Layers

The 4 layers, top to bottom

Layer 1 — Skills (the surface you talk to)

Cowork skills + Markdown / JSON outputs

When you say "run pooya", Claude (Cowork) reads the matching SKILL.md, runs the helper to fetch input from Postgres, generates the agent's output (JSON, Markdown, scoring, whatever shape that agent owns), and runs the helper again to persist back to Postgres. The skill is the API; everything below is implementation.

Lives at rxapply-test/agents/<name>/. 21 of these after Phase C.

Layer 2 — Helpers (the DB boundary)

Python helpers + .bat launchers

Every skill has a <name>.py sibling (~100–300 lines, zero pip deps) that uses subprocess + docker exec to talk to Postgres. The Python is intentionally dumb — it shuttles bytes safely. Claude is the brain; the helper is the hand.

Pattern: every helper exposes fetch/compose/list (read), save/run/write (persist), and ends each persist by shelling out to zirak.py log for the activity feed. Intel agents additionally pipe their payload through paya.py write for shape validation before persistence.

.bat files are convenience launchers — double-click to run. Phase D added smoke-everything.bat as a one-click PASS/FAIL across the whole stack.

Layer 3 — Data plane (the source of truth)

Postgres (Supabase local) — 17 tables

Every state transition the system makes lands in one of 17 tables. The 16-table baseline is owned by supabase/migrations/20260429000000_initial_schema.sql; Phase A added agent_journal via supabase/migrations/20260430000000_agent_journal.sql (apply with apply-migration-agent-journal.bat — never supabase db reset, which wipes test data).

4 · The skill pattern

How a skill is shaped (and why)

Every one of the 21 agents follows the same shape. Once you've seen one, you can read or write any of them. The 10 added in Phase C also follow a "compose → paya/zirak → emit" sub-pattern (see the intel pipeline diagram above).

Anatomy of agents/<name>/
agents/pooya/
├── SKILL.md          ←  what Claude reads when triggered
├── pooya.py          ←  Python helper · DB boundary · ~150 lines
├── <launcher>.bat    ←  optional convenience double-click target
└── <output>.json     ←  saved record of the most recent run

Why each piece exists

SKILL.md

Frontmatter — name + description. The description is what Cowork matches against to decide whether to invoke this skill on a user message. Keep it triggery: include phrasings the user might type.

Body — instructions for Claude. What inputs to expect, what output shape to produce, the workflow steps, voice rules, edge cases.

helper.py

Boundary, not brain. The helper never tries to "understand" the agent's content — it shuttles JSON safely between Claude and Postgres.

Two commands typically: fetch (read JSON to stdout) and save/run (insert/update). Some helpers add enroll, preview, list.

No pip deps. Just subprocess + json + standard lib. Slower than psycopg2, but zero install friction.

.bat launcher

Convenience for testing. Double-click to run the full workflow: fetch → save → verify with a SQL count → print scorecard pass/fail.

In production, n8n would replace these — a workflow node calls the helper directly.

The DB boundary recipe (every helper uses this)

def _psql(sql, *, tA=False, stdin=None): args = ["docker", "exec", "-i", "supabase_db_rxapply-test", "psql", "-U", "postgres", "-d", "postgres", "-v", "ON_ERROR_STOP=1"] if tA: args += ["-tA"] if stdin is None: args += ["-c", sql] r = subprocess.run(args, capture_output=True) # bytes! else: r = subprocess.run(args, input=stdin.encode("utf-8"), capture_output=True) out = r.stdout.decode("utf-8", errors="replace") if r.returncode != 0: sys.exit(...) return out

Why bytes-then-decode? Windows defaults stdout to cp1252 which mangles Farsi/Arabic. Forcing UTF-8 at the boundary is the fix.

For long INSERTs with lots of text

Don't escape inline. Use \set with backtick-cat:

# 1. Write content to host tmp file # 2. docker cp to /tmp/<name>.json inside container # 3. Run psql with: \set my_var `cat /tmp/<name>.json` INSERT INTO ... VALUES (..., :'my_var'::jsonb);

9 · Gotchas

Things that bit us, in order of likelihood

Windows cp1252 stdin/stdout

When you pipe a UTF-8 file into Python via < file.md, Windows decodes as cp1252 by default and dies on Farsi/Arabic bytes. Two fixes already applied: (a) --file argument that reads with explicit UTF-8 encoding, and (b) binary subprocess I/O with explicit decode. Apply the same pattern to any new agent that handles non-ASCII input.

OneDrive locks files mid-write

The whole rxapply-test folder is on Desktop, which is OneDrive-synced. OneDrive grabs locks on log files we're appending to and corrupts the output. Fix: write logs to %TEMP%\, never inside the workspace. If rebuilds get slow because of node_modules sync, move the project to C:\dev\rxapply-test\ outside OneDrive.

Docker auto-detected system proxy

Docker Desktop reads Windows' system proxy by default. If V2RayTun / shecan / similar are installed but not running, Docker tries to route through localhost:10801 and times out. Fix: Settings → Resources → Proxies → both modes set to "No proxy".

Browsers are tier "read" in Cowork's computer-use

When Claude is running on your computer, browser windows are visible-only — no clicks, no typing. To drive a web app from Claude, use the Claude-in-Chrome MCP extension.

UAC prompts can't be clicked from a non-elevated process

Windows UIPI blocks input from lower-integrity processes. Anything that triggers UAC requires your physical click. Once elevated, the elevated cmd window also blocks Claude from sending input.

Re-running agent .bats isn't always idempotent

Pooya, Sepehr, Goyesh, Avang, Mehrban all just insert. Re-running gives you duplicate rows. Bidar uses ON CONFLICT (agent, date) DO UPDATE — safe. Rahbar uses ON CONFLICT (lead_id, sequence_id, step_number) DO NOTHING — safe but silent. Bineh just UPDATEs. Cross-post DRY_RUN flips status — second run is a no-op.

cowork-proxy doesn't auto-restart after reboot

It's a Node process you launched in a terminal. After a reboot, double-click start-proxy.bat to bring it back. Phase A→E made this load-bearing — the admin dashboard, n8n workflows, and prompts editor all break if it's down.

Python text-mode \n→\r\n on Windows

When you write a UTF-8 file with open(path, 'w', encoding='utf-8') on Windows, Python adds \r to every newline — silently expanding the file by ~one byte per line. Bit us during PUT /prompts/:agent round-trip smoke-testing: the round-trip was identical at the wire level but the local file was 100+ bytes larger than the response. Fix: always use binary mode for round-trip comparisons — open(path, 'wb').write(s.encode('utf-8')).

Express .text() mishandles UTF-8

Bit us in the PUT /prompts/:agent route. express.text() defaults to a charset that mis-decodes multibyte UTF-8 (em-dashes, Farsi, Arabic). Fix already in place: switch to express.raw({type: ['text/markdown','text/plain']}) and decode the Buffer explicitly with .toString('utf-8').

Proxy /run-helper resolves <agent>/<agent>.py exactly

If your folder is cross-post/ but the helper is dryrun.py, the proxy can't find it. Fix used: a one-line shim — cross-post/cross-post.py that runpy.run_paths dryrun.py. Same pattern for any future folder/helper-name mismatch.

n8n inside Docker can't reach localhost on the host

All 5 workflow JSONs use http://host.docker.internal:7777/run-helper — that's the magic hostname Docker Desktop (Windows + Mac) provides for "the host machine from inside the container". On Linux you may need to either add --add-host=host.docker.internal:host-gateway when starting n8n, or swap to the Docker bridge IP.

supabase_vector restarts

The Vector container in the Supabase stack sometimes flaps. It's analytics ingestion; nothing in our test phase uses it. Safe to ignore.

★ V3 · The AI-employee platform (Phases K1–K6)

From "instrumented agents" to "manageable employees"

After V2.5 the founder constraint sharpened: "I can't see each agent's output in a way I can understand and measure. Agents reply with nonsense arrays. My goal is for them to behave like human employees — easy to ask, discuss, train, measure, refine, give/restrict access, ask to collaborate or stop, give autonomy or require approval. No coding knowledge needed. Best flagship LLMs. ALL IN MY DASHBOARD, NOWHERE ELSE." V3 is six phases that translate that requirement into shipped surfaces. Every K-phase adds one founder-visible loop with no external tool dependencies (no Lindy, no Slack approvals, no Langfuse — everything embedded in dashboard.html).

K1 · Outputs + Permissions + Inbox

Three changes, one loop:

  • Output renderers — every agent's raw JSON is rendered to a one-line narrative ("afshin drafted a 1080×1080 SVG mock for ‹topic› — 4.2KB · $0.0034") via per-agent templates in dashboard_settings.output_renderers. No more "what does this array mean?"
  • Per-action permission matrix — three modes: auto / ask / blocked, with optional cost threshold. 36 default rows seeded.
  • Inbox — pending actions queue with sidebar badge (amber count), page-title counter (N) RxApply Control Plane, and one-click approve/reject. Polled every 10s.

Modules: permissions.js, output-renderers.js · Migration: 20260508

K2 · Per-agent persistent memory

Each agent now has three memory flavours, scored on retrieval:

  • episodic — past runs / chats (auto-written at every Anthropic call site)
  • semantic — facts the agent should know (founder-authored examples auto-promote here)
  • procedural — rules / corrections (founder corrections auto-promote here)

Retrieval score = importance × recency_decay + tag_match + keyword_match. Top-K injected as a "MEMORY" prompt block at every call. Use-count + last_used_at bump on retrieval, so heavy-used memories surface and unused ones decay.

Surface: Memory tab in Agents detail (filter, manual add, importance stars, "👁 Preview prompt block") · Module: agent-memory.js · Migration: 20260509

K3 · Training & rating

Three founder gestures, all auto-promoting:

  • Rate a run (1–5 stars on a dimension) → agent_evals row · feeds the KPI cards
  • Submit a correction ("you should have done X instead") → auto-writes a procedural memory tagged correction
  • Paste an example ("here's a great X") → auto-writes a semantic memory tagged example

Training compounds without engineering: the next call sees the new rule/example in its prompt automatically. Train tab shows 4 KPIs (avg rating · count · corrections · examples) + low-scoring runs flagged in amber.

  • No web-fetch grounding inside agents (yet). Daneshyar's find-more proposes titles of missing facts; the founder pastes the source for parse. The enrich-from-research permission is seeded as ask for when web fetch lands.
  • No fine-tuning, no embeddings, no RAG vector store. Memory + KB recall use deterministic SQL ranking (importance × recency × tag/keyword match). When the KB grows past ~500 entries we'll switch to pgvector — but not before, because deterministic ranking is debuggable and 500 entries fits comfortably in a top-K SQL scan.
The compound effect. Every K phase looks small in isolation (one table + one module + one panel). The compounding shows up at the call site: a single F5 chat now silently composes brand profile + KB facts (country-detected) + per-agent memory (importance-ranked) + skill spec before the model sees a single user token. The founder edits any one of those four sources in the dashboard once, and every subsequent call across all 23 agents picks it up. That's the human-employee analogy in code: one onboarding doc, one shared knowledge base, one performance review loop, one approval matrix.
